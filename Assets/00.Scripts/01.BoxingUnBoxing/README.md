# 01. 박싱 / 언박싱 — Dictionary와 struct

## 발단

몇백 개가 들어갈 수 있는 `List<T>`를 최악의 경우 1,000번 순회하면서, 그 안에서 계속 `Find`를 호출하는 코드를 봤다. 코드리뷰에서 "이럴 바에는 검색에 유리한 `Dictionary`에 넣는 게 어떻겠냐"고 제안했다.

그런데 이런 반문이 돌아왔다.

> Dictionary에 struct를 넣으면 박싱이 일어나고, 그 상태에서 foreach까지 돌리면 또 박싱이 일어나서, GC 때문에 오히려 프레임 드랍이 생기지 않냐

아닐 것 같은데 확신이 없었다. 그래서 직접 재봤다. 확인할 대상은 **Dictionary, 구조체, foreach의 조합에서 실제로 박싱이 일어나는가**다.

## 측정 결과

Unity 6000.0.72f1 / 에디터(Mono) / Profiler → CPU Usage → Hierarchy → GC Alloc
Dictionary 엔트리 1,000개, 각 케이스를 프레임당 10회 반복.

| 케이스 | 프레임당 GC Alloc | 1회당 |
|---|---|---|
| Dictionary 직접 foreach | 0 B | — |
| `IEnumerable<KeyValuePair<K,V>>`로 받아 foreach | 0.6 KB | 약 60 B — 열거자 박싱 1회 |
| struct 키 조회 — 아무것도 구현 안 함 | 0.9 KB | 약 92 B — 박싱 3회 |
| struct 키 조회 — `IEquatable<T>`만 구현 | 0.3 KB | 약 32 B — 박싱 1회 |
| struct 키 조회 — `IEquatable<T>` + `GetHashCode()` | *(측정 예정)* | |

기준값으로 `object o = i;` 형태의 단순 박싱을 10,000회 돌렸더니 195.3 KB가 나왔다. 정확히 200,000바이트이므로 **박싱 1회당 20바이트**다. 원본 `int`가 4바이트니까 5배로 불어난다. 객체 헤더 16바이트(타입 포인터 8 + 동기화 블록 8)가 붙기 때문이다.

같은 계산으로, 이 실험에 쓴 struct(`int` + `string` 참조)는 페이로드 16바이트 + 헤더 16바이트 = **박싱 1회당 32바이트**다. 조회 1회에 92바이트가 나온 건 32바이트짜리 박싱이 세 번 일어났다는 뜻이다.

## 알아낸 것

### Dictionary에 struct를 넣는다고 무조건 박싱이 일어나지는 않는다

반문의 전제부터가 틀렸다. 박싱이 생기는 건 특정 조건에서고, 그 조건은 세 가지로 갈린다.

### 값(Value) 자리는 거의 안전하다

struct를 값으로 넣는 경우, `ContainsValue()`를 쓰지 않는 이상 박싱은 일어나지 않는다. 값은 "담기는 대상"이라 위치를 계산할 필요가 없고, 그래서 해시도 비교도 필요 없기 때문이다. `ContainsValue()`만 예외적으로 저장된 값들을 처음부터 훑으며 비교한다.

### foreach 자체는 박싱을 만들지 않는다

키에 struct가 있든 값에 struct가 있든, Dictionary를 그냥 foreach로 돌리면 GC가 발생하지 않는다. 0 B다. Dictionary가 반환하는 열거자가 struct이고, 꺼내지는 `KeyValuePair`도 struct라 힙을 쓸 이유가 없다.

**단, `IEnumerable<KeyValuePair<K,V>>` 같은 인터페이스 타입으로 받아서 돌리면 박싱이 일어난다.** foreach는 변수의 선언 타입을 보고 열거자를 가져오는데, 인터페이스를 거치면 struct 열거자가 인터페이스로 박싱되기 때문이다. 다만 이건 **foreach 호출 1회당 열거자 1개**라서 요소 수와 무관하고, 실무에서 치명적인 수준은 아니다. "그냥 순회했는데 박싱이 나더라"는 말이 사실이 되는 유일한 경우이기도 하다.

### 키(Key) 자리가 진짜 문제다

struct를 아무 구현 없이 키로 쓰면 조회 한 번에 박싱이 세 번 일어난다. 이유는 두 갈래다.

**첫째, 키를 비교하는 경로.** Dictionary는 키 비교를 `EqualityComparer<T>.Default`에 위임하는데, 런타임은 이 비교기를 타입에 따라 골라준다. `IEquatable<T>`를 구현하지 않은 타입이면 `object` 기반 비교기가 선택되고, 이 비교기는 `Equals(object)`를 호출한다. 인자도 `object`로 받아야 하고 호출 대상도 힙에 올라가 있어야 하므로 **박싱 2회**가 발생한다. `IEquatable<T>`를 구현하면 제네릭 비교기가 선택되면서 이 2회가 사라진다.

**둘째, 해시코드를 구하는 경로.** Dictionary는 키를 어느 버킷에 넣을지 정하려고 해시코드라는 숫자를 뽑는다. 이때 `GetHashCode()`를 호출하는데, struct가 이걸 재정의하지 않았다면 부모인 `ValueType`의 구현이 불려온다. 그 메서드는 힙 객체를 대상으로 동작하므로 struct를 먼저 박싱해야 하고, 여기서 **박싱 1회**가 더 붙는다. `GetHashCode()`를 재정의하면 struct 자신의 메서드로 직접 호출되면서 사라진다.

두 경로는 완전히 별개다. `IEquatable<T>`만 구현하면 비교 쪽 2회만 없어지고 해시 쪽 1회는 그대로 남는다. 실제로 0.9 KB에서 0.3 KB로만 떨어진 게 그 증거다. 둘 다 해야 0이 된다.

그리고 이 박싱은 조회에서만 생기는 게 아니다. `Add`, `Remove`, `ContainsKey`, 인덱서 접근까지 **키를 다루는 모든 연산**이 같은 경로를 탄다. 그래서 한 번 잘못 쓰면 아주 자주 터진다.

### 정리하면

- 키 자리의 위험은 **GC(박싱)** 이고, 값 자리의 위험은 **복사 비용**이다. 성격이 다른 문제다.
- struct를 키로 쓸 거면 `IEquatable<T>` 구현과 `GetHashCode()` 재정의는 사실상 필수다.
- 이때 `Equals`와 `GetHashCode`는 **같은 필드를 기준으로** 만들어야 한다. "같으면 해시도 같다"가 깨지면 분명히 넣었는데 못 찾는 상황이 생긴다.

## 박싱은 언제 일어나는가

이 실습에서 만난 경로들을 일반화하면 하나로 묶인다. **값 타입이 참조 타입으로 취급되는 순간 박싱된다.** 어디서 그렇게 되느냐가 네 가지다.

**1. `object`로 넘어갈 때** — 매개변수든 변수 대입이든.

```csharp
string.Format("{0}", i);
object o = i;
```

여기서 만난 `Equals(object)`가 이 경우다.

**2. 인터페이스로 취급될 때** — 값 타입이 그 인터페이스를 구현했더라도 마찬가지다.

```csharp
IEnumerable<KeyValuePair<K, V>> iterator = dictionary;
```

`IEnumerable<>`로 받아 foreach를 돌렸을 때 열거자가 박싱된 게 이 경우다.

**3. 오버라이드하지 않은 상속 메서드를 부를 때** — 매개변수가 아예 없어도 일어난다.

```csharp
myStruct.GetHashCode();
myStruct.ToString();
```

`ValueType.GetHashCode()`가 불려서 생긴 박싱 1회가 이 경우다. **"매개변수가 `object`인지 보면 된다"는 규칙으로는 이걸 못 잡는다.** 매개변수가 없으니까.

**4. `params object[]`** — 인자마다 박싱되고 배열 할당까지 붙는다.

### 반대로 안전한 것

제네릭 `T` 매개변수는 박싱하지 않는다. 런타임이 값 타입 전용 코드를 따로 만들어주기 때문이다. `object`와 생김새가 비슷해도 완전히 다르다.

```csharp
void Foo<T>(T value);       // int를 넘겨도 박싱 없음
List<int>.Add(int item);    // 박싱 없음
```

값 타입을 그대로 받는 전용 오버로드가 있는 경우도 안전하다. `StringBuilder.Append(int)`가 그런 예다.

### 확인하는 법

의심되는 호출의 시그니처를 본다. 인자 자리가 `object`나 인터페이스면 박싱이고, `T`나 구체적인 값 타입이면 안전하다.

오버로드가 여러 개일 때는 컴파일러가 어느 것을 고르는지가 관건이라 시그니처만으로는 판단할 수 없다. 그때는 IL을 보거나, 박싱이 불가능한 형태로 바꿔서 같은 숫자가 나오는지 재보면 된다.

## 결론

반문은 틀렸다. Dictionary에 struct를 넣는 것 자체는 박싱을 만들지 않고, foreach도 마찬가지다. 박싱이 문제가 되는 건 struct를 **키로 쓰면서 `IEquatable<T>`와 `GetHashCode()`를 구현하지 않았을 때**뿐이고, 그마저도 몇 줄이면 0으로 만들 수 있다.

제안했던 리팩터링은 그대로 진행됐다. 리뷰어도 스스로 정정하고 `Dictionary`로 바꿔서 적용했다.

내 코드에서 struct를 키로 쓰는 경우는 현재 없지만, 앞으로 쓰게 된다면 두 가지를 반드시 같이 구현해야 한다는 걸 기준으로 삼기로 했다.
