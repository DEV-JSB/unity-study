# 02. 문자열과 GC

## 발단

1편에서 박싱을 재봤지만 와닿지 않았다. `IEquatable`을 구현하지 않은 struct를 Dictionary 키로 쓰는 코드는 실무에서 거의 안 나오기 때문이다.

그래서 이번엔 **게임 개발하면서 훨씬 자주 쓰는 문자열**로 옮겼다. 문자열 연산이 박싱이나 GC와 관계있다는 건 얕게 알고 있었지만 정확히 어떤 방식이 무엇을 만드는지는 몰랐다.

문자열을 만드는 방법은 여러 가지다. 단순 `+` 결합, 보간 `$""`, `string.Format`, `StringBuilder`. 상황마다 어떤 게 박싱을 일으키고 어떤 게 GC를 얼마나 만드는지 직접 재보기로 했다.

## 측정 결과

Unity 6000.0.72f1 / 에디터(Mono) / Profiler → CPU Usage → Hierarchy → GC Alloc
프레임당 6,000회 반복. 1–4번은 `i`(0–5999)를, 5번은 `i / 60`(0–99)을 값으로 사용.

| 케이스 | 프레임당 GC Alloc | 개당 | 내역 |
|---|---|---|---|
| 1. `"Score : " + i` | 441.0 KB | 75.3 B | 중간 문자열 + 최종 문자열 |
| 2. `$"Score : {i}"` | 384.6 KB | 65.6 B | 박싱 + 최종 문자열 |
| 3. `string.Format(...)` | 384.6 KB | 65.6 B | 박싱 + 최종 문자열 |
| 4. `StringBuilder` | 441.0 KB | 75.3 B | 중간 문자열 + 최종 문자열 |
| 5. 값이 바뀔 때만 생성 | **6.6 KB** | — | 문자열을 100개만 만듦 |

문자열 하나의 크기는 **22 + 글자수 × 2** 바이트다. 헤더 16, 길이 필드 4, 널 종료 2에 문자당 2바이트(UTF-16)가 붙는다.

결과 문자열은 평균 11.8글자라 **45.6바이트**다. 그런데 측정값은 65–75바이트였다. 20–30바이트가 더 붙은 것이고, 그게 무엇인지가 이 실험의 내용이다.

- **2·3번** — 45.6 + **20** = 65.6. 그 20바이트는 박싱된 `int`다. 1편에서 잰 20바이트와 정확히 같다.
- **1·4번** — 45.6 + **29.6** = 75.2. 그 29.6바이트는 숫자를 문자열로 바꾼 중간 결과물이다. 평균 3.8자리이므로 22 + 7.6.

5번도 계산이 맞는다. 값이 0–99라 평균 9.9글자, 개당 67.6바이트, 100개면 6,760바이트 = 6.6 KB다.

> 5번은 표시 값이 짧아서(0–99) 개당 크기도 조금 작다. 그래서 감소폭이 정확히 60배가 아니라 66.8배로 나왔다.

## 알아낸 것

### 박싱을 피한 쪽이 오히려 더 컸다

이번 실험에서 가장 뒤집힌 부분이다.

`$""`와 `string.Format`은 인자를 `object`로 받으므로 **박싱한다.** 반대로 `+` 결합과 `StringBuilder.Append(int)`는 **박싱하지 않는다.** 그런데 측정값은 박싱하는 쪽이 15% 더 작았다.

이유는 서로 다른 것을 만들기 때문이다.

**박싱하는 방식**은 숫자를 결과 버퍼에 자릿수로 직접 써넣는다. 중간 문자열이 필요 없다. 대신 인자를 넘기는 과정에서 박싱이 일어난다.

**박싱하지 않는 방식**은 숫자를 먼저 `"5999"` 같은 **문자열로 바꾼 다음** 붙인다. 박싱은 없지만 쓰고 버릴 문자열이 하나 더 생긴다.

그리고 **중간 문자열 30바이트가 박싱 20바이트보다 비싸다.** 어느 쪽이 정답이라고 할 수 없고, 장단점이 분명히 갈린다.

여기서 얻은 교훈은 **"박싱을 피했다"가 "할당이 적다"를 뜻하지 않는다**는 것이다. 1편만 하고 나면 박싱만 쫓게 되는데, 박싱은 여러 비용 중 하나일 뿐이다.

### 보간 문자열은 `string.Format`이다

2번과 3번이 384.6 KB로 **소수점까지 정확히 같았다.**

"비슷하다"면 아무것도 말할 수 없지만 "정확히 같다"는 **두 코드가 동일한 것으로 컴파일됐다**는 뜻이다. 즉 `$"Score : {i}"`는 컴파일 시점에 `string.Format("Score : {0}", i)`로 바뀐다. 실행 시점에는 구분 자체가 없다.

측정으로 컴파일러의 동작을 알아낸 셈이다.

### StringBuilder는 이 상황에서 이점이 없다

4번이 단순 결합과 똑같이 441.0 KB가 나왔다.

StringBuilder의 장점은 **누적 과정에서 중간 결과가 쌓이지 않는다**는 것이다. 버퍼도 한 번 만들어 계속 재사용한다. 그런데 이번엔 조각이 두 개뿐이었고, 결정적으로 마지막에 `ToString()`을 부른다. 버퍼는 `char[]`이고 결과는 `string`이라, 그 사이에서 최종 문자열이 반드시 만들어진다.

기준은 **"얼마나 자주 만드느냐"가 아니라 "한 번에 몇 조각을 붙이느냐"**다.

- 조각 두세 개를 한 줄에서 붙이는 경우 → 컴파일러가 `Concat` 하나로 합쳐준다. StringBuilder는 불필요하다.
- **루프를 돌며 계속 누적하는 경우** → 반복마다 점점 커지는 새 문자열이 생긴다. 여기서 StringBuilder가 이긴다.

### 결합이 박싱하지 않는다는 것은 어떻게 확인했나

2·3번은 `string.Format(string, object)`라는 **시그니처만 보고** 박싱을 확정할 수 있었다. 인자가 `object`니 값 타입을 넘기려면 박싱 외에 방법이 없다.

그런데 `"Score : " + i`는 시그니처를 볼 수가 없다. `+`는 연산자라 **소스 코드에 메서드 이름이 아예 없기 때문**이다. 컴파일러가 `string.Concat`의 여러 오버로드 중 하나를 고르는데, 어느 것을 고르는지가 코드에 안 적혀 있다.

그래서 케이스를 하나 추가해서 재봤다.

```csharp
_str = "Score : " + i.ToString();   // 명시적으로 문자열로 바꿔서 넘김 → 박싱 불가능
```

결과가 1번과 **똑같은 441.0 KB**였다. 1번도 원래 박싱을 하지 않고 있었다는 뜻이다. 컴파일러가 이미 `ToString()`을 부르고 문자열끼리 붙이고 있었다.

시그니처로 판단할 수 없을 때는 **박싱이 불가능한 형태로 바꿔서 숫자가 같은지 보면 된다.**

### 그래서 만드는 방법은 중요하지 않다

1–4번은 65–75바이트 사이에서 **15% 차이**로 다툰다. 그런데 5번은 441.0 KB를 6.6 KB로 만들었다. **66배다.**

방법을 고르는 것과 만들지 말지를 정하는 것은 자릿수가 다른 문제다.

5번이 한 일은 단순하다. 직전에 만든 값을 필드에 기억해두고, 값이 그대로면 문자열을 만들지 않는다. 조건문 하나가 전부다.

```csharp
if (value != _lastValue)
{
    _str = "Score : " + value;
    _lastValue = value;
}
```

실전 UI가 정확히 이 구조다. `Update()`는 매 프레임 호출되지만 체력이나 점수는 가끔만 바뀐다. 그런데 조건 없이 매 프레임 갱신하면, 화면에 보이는 글자는 똑같은데 문자열만 계속 새로 만들어 버린다.

## 결론

**박싱은 매번 일어나지 않는다. 하지만 문자열을 만드는 이상 GC는 피할 수 없다.**

결과 문자열 자체가 힙 할당이기 때문이다. 박싱을 없애든 중간 문자열을 없애든 그 45.6바이트는 남는다. 그래서 방법을 바꾸는 것으로는 15%가 한계다.

그러므로 순서는 이렇게 잡는다.

1. **애초에 만들지 않는다.** 값이 바뀔 때만 갱신한다. 66배다. 대부분 여기서 끝난다.
2. **만들어야 하면 읽기 좋은 것을 쓴다.** 15% 차이 때문에 가독성을 버릴 이유가 없다. 보간이 제일 읽기 쉽고 측정상 제일 작기까지 했다.
3. **루프로 누적해야 하면 StringBuilder를 쓴다.**

## 측정하지 않았지만 알아둘 것

아래는 이번에 재지 않았다. 결과 표와 구분해서 적어둔다.

### UI 텍스트는 문자열을 아예 안 만들 수 있다

TextMeshPro의 `SetText`에는 포맷 인자를 받는 오버로드가 있다.

```csharp
textMesh.SetText("HP: {0}", currentHp);
```

포맷 문자열은 리터럴이라 컴파일 시점에 이미 존재하고, 숫자는 TMP가 자기 내부 `char[]` 버퍼에 자릿수를 직접 쓴다. 인자 타입도 `float`으로 명시돼 있어 박싱이 없다. **문자열 객체가 하나도 만들어지지 않는다.**

`SetText(StringBuilder)` 오버로드도 있다. `ToString()`을 부르지 않고 StringBuilder의 문자를 직접 읽어가므로, 이번 실험에서 StringBuilder가 손해 본 마지막 단계까지 없앨 수 있다.

### Debug.Log

문자열을 만들어 넘기는 것이므로 위의 모든 비용이 그대로 적용된다. 게다가 로그 파일에 쓰는 File I/O가 따라붙고, **호출 지점을 역추적해 스택 트레이스를 문자열로 만드는 비용**이 사실 제일 크다.

빌드에도 그대로 남으므로, 매 프레임 도는 코드에 넣지 않도록 주의하고 조건부 컴파일로 걷어내는 방법도 고려할 만하다.
